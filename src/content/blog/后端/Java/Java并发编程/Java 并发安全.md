## 一、JUC 包下常用的类有哪些？

JUC 指 `java.util.concurrent` 包，提供了线程池、并发集合、同步工具类和原子类等并发编程组件。

### 1. 线程池相关

- `ThreadPoolExecutor`：线程池的核心实现，可以配置核心线程数、最大线程数、任务队列、线程工厂和拒绝策略等参数。
- `Executors`：线程池工厂类，提供 `newFixedThreadPool()`、`newCachedThreadPool()`、`newSingleThreadExecutor()` 等创建方法。实际项目中通常根据任务特点直接配置 `ThreadPoolExecutor`，避免队列或线程数量不受控制。

### 2. 并发集合

- `ConcurrentHashMap`：线程安全的哈希表，适合多线程环境下存储和访问键值对。JDK 1.7 主要使用分段锁，JDK 1.8 以后采用 CAS、`synchronized` 和桶级别的控制，锁粒度更细。
- `CopyOnWriteArrayList`：写操作时复制底层数组，读操作可以访问旧数组，适合读多写少的场景。

### 3. 同步工具类

- `CountDownLatch`：让一个或多个线程等待一组任务完成。计数器减到零后，等待线程继续执行。计数器一般只能使用一次。
- `CyclicBarrier`：让一组线程相互等待，直到所有线程到达屏障点后一起继续执行。屏障可以重复使用，适合分阶段协作的场景。
- `Semaphore`：信号量，用于限制同时访问某个资源的线程数量，例如数据库连接或线程池中的并发任务数。

### 4. 原子类

- `AtomicInteger`：提供整数的原子更新操作，例如自增、自减和比较并交换。
- `AtomicLong`：提供 `long` 类型的原子更新操作。
- `AtomicReference`：提供对象引用的原子更新，适合无锁更新共享对象引用。

原子类通常基于 CAS 实现，可以减少简单共享变量更新对锁的依赖；但涉及多个变量的一致性时，仍然需要使用锁或其他同步机制。

## 二、怎么保证多线程安全？

保证多线程安全，核心是正确处理共享数据的可见性、原子性和有序性。常见方式如下。

### 1. 使用 `synchronized`

`synchronized` 可以修饰方法或代码块，通过对象监视器锁保证同一时刻只有一个线程执行受保护的代码。

```java
public synchronized void update() {
    // 同一时刻只允许一个线程执行
}

public void anotherUpdate() {
    synchronized (lockObject) {
        // 保护共享数据
    }
}
```

### 2. 使用 `volatile`

`volatile` 保证变量的修改能够及时被其他线程看到，并限制相关指令重排序：

```java
private volatile boolean running = true;
```

但 `volatile` 不能保证复合操作的原子性，例如 `count++` 仍然可能发生数据竞争。需要原子更新时，应使用原子类或锁。

### 3. 使用 `Lock` 和 `ReentrantLock`

`Lock` 接口提供了比 `synchronized` 更灵活的锁机制，`ReentrantLock` 是它的常用实现，支持可中断加锁、超时尝试和公平锁等功能。

```java
private final ReentrantLock lock = new ReentrantLock();

public void update() {
    lock.lock();
    try {
        // 保护共享数据
    } finally {
        lock.unlock();
    }
}
```

使用 `Lock` 时必须在 `finally` 中释放锁，避免异常导致锁无法释放。

### 4. 使用原子类

`java.util.concurrent.atomic` 包提供了基于 CAS 的原子类，例如 `AtomicInteger`、`AtomicLong` 和 `AtomicReference`，适合对单个变量进行原子更新。

```java
AtomicInteger counter = new AtomicInteger(0);
int value = counter.incrementAndGet();
```

### 5. 使用 `ThreadLocal`

`ThreadLocal` 为每个线程保存独立的变量副本，线程之间互不影响，可以减少共享变量带来的竞争：

```java
ThreadLocal<Integer> localValue = new ThreadLocal<>();
localValue.set(10);
Integer value = localValue.get();
```

在线程池中使用 `ThreadLocal` 时，任务结束后应及时调用 `remove()`，避免线程复用导致数据残留。

### 6. 使用并发集合和 JUC 工具类

- 使用 `ConcurrentHashMap`、`CopyOnWriteArrayList`、`ConcurrentLinkedQueue` 等并发集合，避免直接操作非线程安全集合。
- 使用 `CountDownLatch`、`CyclicBarrier`、`Semaphore` 等工具类完成线程等待、协作和资源数量控制。

选择同步方式时，应优先减少共享可变状态；必须共享时，再根据场景选择锁、原子类、线程安全集合或并发工具类。

## 三、Java 中有哪些常用的锁，适合什么场景？

锁用于协调多个线程对共享资源的访问，避免数据竞争和状态不一致。常见类型如下。

### 1. 内置锁：`synchronized`

`synchronized` 是 Java 提供的内置锁，可以修饰实例方法、静态方法或代码块。线程进入同步区域时获取锁，离开后自动释放锁；其他线程获取同一把锁时会等待。

它使用简单，异常情况下也能自动释放锁，适合大多数简单的互斥场景。锁的对象需要选择合适，避免锁范围过大导致并发性能下降。

### 2. 显式锁：`ReentrantLock`

`ReentrantLock` 是 `Lock` 接口的常用实现，通过 `lock()` 和 `unlock()` 获取、释放锁。相比 `synchronized`，它提供了更灵活的能力：

- 可中断地获取锁；
- 设置获取锁的超时时间；
- 选择公平锁或非公平锁；
- 支持多个 `Condition` 条件队列。

它适合需要精细控制锁行为的场景，但使用时必须确保最终释放锁。

### 3. 读写锁：`ReadWriteLock`

`ReadWriteLock` 通常使用 `ReentrantReadWriteLock` 实现：

- 读锁允许多个线程同时持有，适合读取远多于写入的场景。
- 写锁具有排他性，写入时不允许其他线程读写。

如果写操作频繁，读写锁的维护成本可能抵消并发读取带来的收益，需要根据实际竞争情况选择。

### 4. 悲观锁和乐观锁

- **悲观锁**：访问数据前先加锁，假设数据很可能被其他线程修改。`synchronized` 和 `ReentrantLock` 都属于常见的悲观锁，适合冲突频繁的场景。
- **乐观锁**：不提前锁定资源，在更新时检查数据是否被修改过，常通过版本号、时间戳或 CAS 实现，适合冲突较少、读操作较多的场景。

乐观锁冲突后通常需要重试或返回失败；悲观锁则会让竞争线程等待锁释放。

### 5. 自旋锁

自旋锁不会让线程立即阻塞，而是让线程循环检查锁是否可用，通常基于 CAS 实现。它适合锁持有时间很短、线程等待时间较少的场景，可以减少线程阻塞和唤醒的开销。

如果锁竞争激烈或持有时间较长，自旋会持续消耗 CPU，反而可能降低性能。

### 6. 选择建议

- 普通互斥访问：优先考虑 `synchronized`。
- 需要超时、中断或多个条件队列：考虑 `ReentrantLock`。
- 读多写少：考虑读写锁或合适的并发容器。
- 冲突较少、更新对象较简单：可以考虑乐观锁或原子类。
- 等待时间极短：可以考虑自旋；不要对长时间任务使用自旋锁。

## 四、`synchronized` 静态方法和普通方法有什么区别？

两者的核心区别是锁对象不同，因此影响的并发范围也不同。

### 1. 锁对象不同

- **普通同步方法**：锁住当前对象实例，也就是 `this`。同一个对象实例的同步方法同一时间只能由一个线程执行。
- **静态同步方法**：锁住当前类的 `Class` 对象，例如 `User.class`。同一个类的所有实例共享这把类锁。

### 2. 作用范围不同

- 多个线程访问同一个对象实例的同步普通方法时，会互相等待。
- 多个线程访问不同对象实例的同步普通方法时，通常不会互相影响，因为锁对象不同。
- 不管创建了多少个对象，同一个类的静态同步方法同一时间通常只能由一个线程执行。

### 3. 两种锁不是同一把锁

普通同步方法锁住的是实例对象，静态同步方法锁住的是 `Class` 对象，两者可以同时执行，互不阻塞。

因此，使用 `synchronized` 时要先确定需要保护的是：

- 某个对象实例中的共享数据：使用普通同步方法或锁住具体实例。
- 整个类共享的静态数据：使用静态同步方法或锁住对应的 `Class` 对象。

## 五、怎么理解可重入锁？

可重入锁允许同一个线程在已经持有锁的情况下，再次获取同一把锁，而不会被自己阻塞。`ReentrantLock` 和 `synchronized` 都支持可重入。

可重入锁内部会记录持有锁的线程和重入次数：

```text
初始状态：0
第一次加锁：1
第二次加锁：2
第三次加锁：3
第一次解锁：2
第二次解锁：1
第三次解锁：0
```

只有计数器减到 `0`，锁才算完全释放，其他线程才有机会获取它。因此，完整过程是：

```text
0 → 1 → 2 → 3 → 2 → 1 → 0
```

如果加锁和解锁次数不匹配，例如加锁三次只解锁两次，锁仍然由当前线程持有，其他线程会继续等待。

### 为什么已经加锁了还要再次加锁？

并不是所有情况下都需要再次加锁，只有当同一个线程在持锁期间又进入了同一把锁保护的方法或代码块时，才会发生重复加锁，例如：

- 一个同步方法调用同一个对象的另一个同步方法；
- 加锁方法内部调用了自身，产生递归；
- 多层方法调用最终再次进入同一把锁。

如果锁不可重入，线程第一次持有锁后再次申请同一把锁，就会一直等待自己释放锁，形成自我阻塞。可重入锁通过记录持有线程和重入次数，允许同一个线程继续执行，并在每层方法退出时减少计数，直到计数归零后才真正释放锁。

## 六、JVM 对 `synchronized` 做了哪些优化？

JVM 会根据锁的竞争情况和代码特点，对 `synchronized` 进行优化。常见方向包括锁升级、锁消除、锁粗化和自适应自旋。

### 1. 锁升级

锁竞争加剧时，锁可能从低开销的实现逐步升级为更重量级的实现，以保证线程安全和数据一致性。传统资料通常会介绍无锁、偏向锁、轻量级锁和重量级锁等状态。

需要注意：偏向锁是较早版本 HotSpot 中的优化机制，在较新的 JDK 中已经被弱化或移除；学习时应以当前 JDK 的实际实现为准。锁升级通常只会增加同步成本，不会为了性能安全地自动降级。

### 2. 锁消除

如果 JVM 通过逃逸分析判断某个锁对象不会被其他线程访问，就可能发现这段同步没有实际竞争，从而消除不必要的加锁和解锁操作。

锁消除不会改变程序的正确性，只会针对确定不存在并发竞争的同步代码进行优化。

### 3. 锁粗化

如果同一个线程在短时间内对同一个对象反复加锁和解锁，JVM 可能将多个连续的同步区域合并为一个更大的同步区域，减少频繁加锁和解锁的开销。

锁粗化可以降低同步操作次数，但也可能扩大锁的持有范围，使其他线程等待更久，因此需要在减少锁开销和并发度之间取得平衡。

### 4. 自适应自旋

轻量级锁竞争失败后，线程可能先进行短暂自旋，而不是立即挂起并进行上下文切换。如果锁很快被释放，自旋线程可以直接获得锁，避免线程阻塞和唤醒的开销。

自旋次数会根据之前的竞争情况动态调整：如果之前自旋成功，后续可能增加自旋次数；如果经常失败，则可能减少自旋或直接阻塞。锁持有时间较长、竞争激烈时，过度自旋会浪费 CPU。

这些优化属于 JVM 实现细节，不应依赖某一种锁状态或具体升级过程来设计业务逻辑。业务代码只需要正确使用同步机制，具体优化交给 JVM 完成。

## 七、介绍一下 AQS

AQS 全称是 `AbstractQueuedSynchronizer`，即抽象队列同步器。它是 Java 并发包中用于构建锁、同步器和协作工具的基础框架，`ReentrantLock`、`Semaphore`、`CountDownLatch` 和 `ReentrantReadWriteLock` 等都在不同程度上使用了 AQS。

### 1. AQS 的核心组成

- **同步状态 `state`**：AQS 使用一个 `volatile int` 类型的状态变量表示资源是否可用以及当前占用情况。子类根据自身需求解释这个值，例如重入次数、剩余许可数或未完成任务数。
- **同步队列**：获取资源失败的线程会被封装成节点，加入一个基于 CLH 思想改造的 FIFO 双向队列中，并在适当时机挂起等待。
- **获取与释放模板**：AQS 负责排队、阻塞和唤醒，具体的资源获取与释放规则由子类实现。

### 2. AQS 的基本工作流程

1. 线程尝试获取同步资源。
2. 如果资源可用，直接修改 `state` 并继续执行。
3. 如果资源不可用，线程进入同步队列并阻塞等待。
4. 持有资源的线程释放资源，更新 `state`。
5. AQS 唤醒队列中的后继节点，等待线程重新尝试获取资源。

AQS 通常使用 CAS 更新状态，并结合队列和 `LockSupport.park()` / `unpark()` 完成线程的阻塞与唤醒，避免让线程一直占用 CPU 空转。

### 3. 独占模式和共享模式

- **独占模式**：同一时刻只能有一个线程成功获取资源，例如 `ReentrantLock`。
- **共享模式**：多个线程可以同时获取资源，但可获取的数量受到限制，例如 `Semaphore`；`CountDownLatch` 也使用共享方式让多个等待线程在条件满足后继续执行。

`ReentrantReadWriteLock` 同时使用了两种思路：读锁允许多个线程共享，写锁则要求独占。AQS 通过 `state` 的不同位或不同约定来记录读写状态。

### 4. AQS 与具体同步器的关系

AQS 本身不是一个可以直接使用的具体锁，它更像是一个同步器模板：

- AQS 负责维护状态、同步队列、线程阻塞和唤醒。
- 具体同步器负责实现 `tryAcquire()`、`tryRelease()` 等方法，定义什么情况下算获取成功、什么情况下算释放成功。

这种设计将通用的排队和阻塞逻辑抽取出来，具体锁只需要实现自己的资源管理规则，就可以复用 AQS 的并发控制能力。

### 5. AQS 的条件队列

AQS 还提供了 `ConditionObject`，用于实现类似 `wait()` / `notify()` 的条件等待机制。调用 `await()` 的线程会暂时释放锁并进入条件队列；其他线程调用 `signal()` 后，等待节点会被转移到同步队列，之后重新竞争锁。

因此，AQS 不仅可以支持互斥锁，也可以支持带条件等待、许可控制、倒计时和读写协作等多种同步场景。

## 八、CAS 和 AQS 有什么关系？

CAS 和 AQS 处于不同层次：

- **CAS** 是一种底层的原子更新机制，比较内存中的旧值和预期值，匹配时才替换为新值。
- **AQS** 是构建锁和同步器的框架，负责维护同步状态、等待队列以及线程的阻塞和唤醒。

### 1. AQS 如何使用 CAS？

AQS 使用一个 `volatile` 的 `state` 变量表示同步状态，并通过 CAS 安全地修改它：

- 线程尝试获取资源时，使用 CAS 将 `state` 更新为新的状态。
- CAS 成功，说明资源获取成功，线程继续执行。
- CAS 失败，说明状态已经被其他线程修改，线程需要重新尝试，或者进入 AQS 的同步队列等待。
- 线程释放资源时，也会通过更新 `state` 反映资源已经释放，并唤醒等待线程。

### 2. 两者如何配合工作？

CAS 负责“状态更新是否成功”，AQS 负责“失败后如何排队等待以及何时唤醒”：

```text
线程尝试获取资源
        ↓
CAS 更新 state
        ↓
成功：继续执行
失败：进入 AQS 等待队列并阻塞
        ↓
其他线程 release
        ↓
更新 state，并唤醒后继线程
```

所以，CAS 本身只解决一次原子比较和更新；AQS 则在 CAS 的基础上补充了等待队列、阻塞、唤醒和资源获取规则，形成完整的同步器框架。

### 3. 一句话总结

**CAS 是 AQS 用来更新同步状态的底层工具，AQS 是利用 CAS 加上队列管理和线程阻塞唤醒机制构建出来的高级并发框架。**

## 九、ThreadLocal 的作用、原理和常见问题是什么？

### 1. ThreadLocal 的作用

`ThreadLocal` 用于为每个线程保存一份独立的数据副本。不同线程通过同一个 `ThreadLocal` 对象访问数据时，拿到的也是各自线程保存的值，线程之间互不影响。

它适合保存与当前线程相关的上下文信息，例如用户上下文、事务上下文、请求标识或日期格式化对象等，但不适合在线程之间共享数据。

### 2. ThreadLocal 的基本原理

`ThreadLocal` 并不是把数据存放在自己内部，而是把数据存放在当前线程对象的 `ThreadLocalMap` 中：

```text
当前线程 Thread
        ↓
ThreadLocalMap
        ↓
多个 Entry
        ↓
ThreadLocal 对象 → 当前线程对应的 Value
```

调用 `set(value)` 时，`ThreadLocal` 会先获取当前线程，再把键值对保存到当前线程的 `ThreadLocalMap` 中；调用 `get()` 时，再从当前线程的 Map 中取出对应值。

### 3. ThreadLocalMap 中的 Key 和 Value 是什么？

| 位置 | 保存内容 |
| --- | --- |
| Key | 当前的 `ThreadLocal` 对象，Entry 中以弱引用的形式保存 |
| Value | 调用 `set()` 保存的业务对象，以强引用的形式保存 |
| Map 所属 | 当前线程对象，而不是 ThreadLocal 对象 |

例如，一个 `ThreadLocal<String>` 保存了用户名称，那么：

- Key 是这个 `ThreadLocal<String>` 实例的引用；
- Value 是当前线程设置的字符串；
- 其他线程即使使用同一个 ThreadLocal，也会从自己的 Map 中读取自己的 Value。

每创建一个 ThreadLocal，当前线程的 Map 中通常就会增加一个对应的 Entry。

### 4. 为什么 Key 使用弱引用？

`ThreadLocalMap` 的 Entry 继承了弱引用，目的是在线程外部不再持有某个 ThreadLocal 时，允许这个 Key 被垃圾回收，避免 ThreadLocal 对象本身长期占用内存。

但 Entry 的 Value 是强引用，因此可能出现这种情况：

```text
ThreadLocal 对象被回收
        ↓
Entry 的 Key 变成 null
        ↓
Value 仍然被当前线程引用
        ↓
Value 可能长期无法回收
```

JDK 会在线程后续访问 ThreadLocalMap 时顺便清理部分 Key 已经失效的 Entry，但这种清理不是立即、全面发生的，不能只依赖它解决内存问题。

### 5. ThreadLocal 的常见问题

- **内存泄漏**：线程长时间存活时，失效 Entry 中的 Value 可能长期保留，在线程池线程中尤其需要注意。
- **线程池数据污染**：线程池会复用工作线程，如果任务结束后没有清理 ThreadLocal，下一个任务可能读取到上一个任务留下的数据。
- **隐式状态过多**：数据不通过方法参数传递，调用链难以追踪，滥用会增加代码理解和测试难度。
- **线程范围有限**：ThreadLocal 数据只属于当前线程，不会自动传递给其他线程、异步任务或线程池任务。
- **误用 InheritableThreadLocal**：它只适合简单的父子线程传值，在线程池复用线程时可能产生过期数据，不适合作为通用上下文传递方案。

### 6. 如何解决和正确使用？

- 使用完后及时调用 `remove()`，尤其是在请求线程和线程池任务中。
- 将清理操作放在 `finally` 中，确保任务出现异常时也能执行。
- 对线程池中的 ThreadLocal 数据设置明确的生命周期，不让业务数据跨任务残留。
- 优先使用方法参数传递明确的业务数据，只有确实需要线程隔离时再使用 ThreadLocal。
- 跨线程或异步场景需要传递上下文时，优先使用明确的上下文参数或框架提供的上下文传播机制。
- 对长期使用的 ThreadLocal，可以使用明确管理生命周期的 `static final` 实例，但仍然需要在适当时机调用 `remove()`。

ThreadLocal 的重点可以概括为：**数据存在线程的 Map 中，Key 是 ThreadLocal，Value 是线程独有的数据；用完必须清理，避免在线程池中产生内存泄漏和数据污染。**

## 十、CAS 有什么缺点？

CAS 虽然避免了部分锁竞争，但并不是所有并发场景的最佳方案，主要有以下三个缺点。

### 1. ABA 问题

线程第一次读取到值 `A`，准备更新时，其他线程可能先把值改成 `B`，之后又改回 `A`。此时 CAS 只比较最终值，可能认为数据从未改变过，但实际上中间已经发生了变化。

如果业务需要识别值是否经历过变化，可以使用 `AtomicStampedReference`，为共享值增加版本号，让 CAS 同时比较值和版本。

### 2. 循环重试会消耗 CPU

CAS 失败后通常需要循环读取最新值并重新尝试。如果竞争持续时间较长，线程会不断自旋，消耗 CPU 资源，却没有真正完成有效工作。

因此，CAS 更适合冲突较少、更新很快的场景。高竞争或操作耗时较长时，可以考虑锁、退避策略或其他并发结构。

### 3. 只能直接保证一个共享变量的原子更新

CAS 适合更新一个共享变量或一个对象引用。如果一个业务操作需要同时修改多个变量，就很难只依靠单次 CAS 保证整体一致性。

这类场景通常应使用锁、不可变对象、原子引用封装整体状态，或者重新设计数据结构，避免多个变量之间出现中间不一致状态。

总体来说，CAS 适合简单、快速、冲突较少的原子更新；面对复杂的多变量操作或激烈竞争时，不能盲目用 CAS 代替锁。

## 十一、`volatile` 关键字有什么作用？

`volatile` 主要有两个作用：保证变量的可见性，以及禁止部分不安全的指令重排序。

### 1. 保证可见性

一个线程写入 `volatile` 变量后，其他线程读取这个变量时能够看到最新值。按照 JMM 的 happens-before 规则，对 `volatile` 变量的写操作，会先于后续线程对同一个变量的读操作生效。

因此，`volatile` 适合表示线程之间共享的状态标志，例如任务是否需要停止、配置是否已经更新等。

### 2. 禁止特定的指令重排序

编译器和处理器可能为了优化性能调整指令顺序。`volatile` 的读写会建立必要的内存屏障，限制相关读写操作跨越 volatile 变量重排序，从而保证线程观察到的执行顺序符合 JMM 规则。

可以简单理解为：

- `volatile` 写操作之前的普通写操作，不能被重排到 volatile 写之后。
- `volatile` 读操作之后的普通读写操作，不能被随意重排到 volatile 读之前。

不同 CPU 架构和 JDK 版本实现内存屏障的指令可能不同，业务代码不需要依赖具体的底层汇编实现。

### 3. `volatile` 不保证复合操作的原子性

`volatile` 只能保证单次读写的可见性和顺序，不能把“读取、计算、写回”组合成一个不可分割的操作。因此，`volatile int count` 仍然不能安全地执行 `count++`。

需要保证复合操作原子性时，应使用 `synchronized`、`Lock`、`AtomicInteger` 等机制。

### 4. 使用总结

- 需要让多个线程及时看到一个状态变化：可以考虑 `volatile`。
- 需要保证多个步骤作为一个整体执行：使用锁或原子类。
- 需要保护多个变量之间的一致性：不能只依赖 `volatile`。
- `volatile` 解决的是可见性和有序性，不等于线程安全的万能方案。

## 十二、什么是公平锁和非公平锁？

- **公平锁**：多个线程按照申请锁的先后顺序排队，通常由等待队列中的线程依次获取锁。它能减少线程长期得不到执行机会的情况，但线程排队、阻塞和唤醒的成本较高，整体吞吐量可能较低。
- **非公平锁**：线程获取锁时可以直接尝试抢占。获取成功就直接执行，失败后再进入等待队列。它减少了排队和线程切换，通常吞吐量更高，但等待时间较长的线程可能出现饥饿。

### 非公平锁为什么通常吞吐量更高？

公平锁即使锁刚刚释放，也通常需要按照队列顺序唤醒等待线程。线程从阻塞状态恢复需要线程调度和上下文切换，存在额外开销。

非公平锁允许新到达的线程直接尝试获取刚释放的锁。如果获取成功，就减少了等待线程的唤醒和切换过程，因此在高并发、锁持有时间较短的场景下通常有更高吞吐量。

### 如何选择？

- 对执行顺序和等待时间比较敏感，不能接受线程长期得不到锁：考虑公平锁。
- 更关注整体吞吐量，且能够接受线程等待时间存在差异：通常使用非公平锁。
- `ReentrantLock` 默认使用非公平策略；`synchronized` 不保证严格的公平顺序。

公平锁也不能保证线程绝对按照业务提交顺序执行，最终仍会受到线程调度和锁竞争情况影响。

## 十三、什么情况下会产生死锁？如何解决？

死锁是多个线程相互等待对方持有的资源，导致所有线程都无法继续执行。死锁通常需要以下四个条件同时成立：

1. **互斥条件**：资源同一时间只能被一个线程占用。
2. **持有并等待**：线程已经持有一个资源，同时继续等待其他资源。
3. **不可剥夺**：线程持有的资源不能被其他线程强行夺走，只能由持有线程主动释放。
4. **循环等待**：多个线程之间形成首尾相接的资源等待环路。

### 常见解决方式

- **固定加锁顺序**：所有线程按照相同顺序获取多把锁，破坏循环等待条件。
- **一次性获取资源**：在开始执行前一次申请所需的全部资源，避免持有资源后继续等待。
- **缩小锁的范围**：只在必要的代码区域加锁，并尽快释放锁，减少持有锁的时间。
- **使用可超时或可中断的锁**：获取锁失败时主动放弃、重试或执行降级逻辑，不让线程无限等待。
- **减少锁的数量**：使用并发容器、原子类或不可变对象，降低多把锁互相依赖的概率。

### 死锁的排查

如果程序出现线程长期卡住、请求持续超时等现象，可以查看线程转储，分析线程当前持有的锁和正在等待的锁。JVM 工具通常能够检测出典型的锁循环。

解决死锁的关键不是单纯增加锁，而是破坏四个必要条件中的至少一个，最常用的方式是统一加锁顺序和设置获取锁的超时时间。
