## 一、什么是 Java 的垃圾回收？如何触发？

垃圾回收（Garbage Collection，GC）是 JVM 自动管理内存的机制：识别满足回收条件的对象，回收其占用的内存。它主要管理堆，也可能涉及类卸载等操作；仍被强引用持有的无用对象，不能依靠 GC 自动解决泄漏。

常见触发情况包括：

- **分配压力**：对象分配空间不足时，JVM 可能触发 GC，尝试腾出空间。例如新生代空间不足引发年轻代回收；回收后仍无法满足分配，可能进一步回收或抛出 OOM。
- **达到回收器阈值**：不同回收器会根据堆占用、分配速度和停顿目标等决定何时启动回收。G1 可以在达到并发标记启动阈值时开始标记，不必等到堆耗尽。
- **元空间分配压力**：可能触发支持类卸载的 GC，尝试回收不再使用的类及其元数据，具体行为取决于回收器和配置。
- **显式请求**：调用 `System.gc()` 或 `Runtime.getRuntime().gc()` 请求回收，但不保证立即执行，也不保证回收所有不可达对象；相关配置可以让 JVM 忽略请求。

`-Xms`、`-Xmx` 等参数影响堆容量，从而间接影响 GC 频率，并不是直接触发 GC 的操作。具体回收类型和时机取决于回收器，不能将老年代空间不足一概等同于 Full GC。

## 二、判断垃圾的方法有哪些？

常见思路有**引用计数法和可达性分析**，HotSpot 等主流 JVM 主要采用可达性分析。

### 1. 引用计数法

为每个对象维护引用计数：新增引用时加一，引用失效时减一，计数为零时可以回收。

简单引用计数无法处理循环引用：两个对象相互引用，即使外部已无法访问它们，计数仍不为零，导致无法回收。维护计数也有额外开销。

### 2. 可达性分析

从 **GC Roots（垃圾回收根）** 出发，沿引用关系寻找对象。若对象无法从 GC Roots 到达，就可以作为待回收对象处理；因此，无外部可达路径的循环引用不会阻止回收。

常见的根引用来源包括：

- 活跃线程栈中的对象引用，例如局部变量和参数。
- JNI 的本地引用、全局引用等。
- JVM 内部保持存活对象的引用，例如部分系统对象和活动监视器相关引用。

存活类的静态字段也可能形成通往对象的强引用链。分析时应关注完整的可达路径，不能认为所有静态字段或字符串常量池中的对象都永远不会回收。

实际 GC 还需要按软引用、弱引用、虚引用的规则处理对象，不能只按是否存在任意引用来判断。

## 三、垃圾回收算法有哪些？

常见基础算法有标记—清除、复制和标记—整理；分代回收则是根据对象存活特点组合使用这些算法的策略。

| 算法 | 基本过程 | 优点 | 主要代价 |
| --- | --- | --- | --- |
| 标记—清除 | 标记存活对象，再回收未标记对象 | 不需要移动存活对象 | 可能产生内存碎片 |
| 复制 | 将存活对象复制到另一片区域，回收原区域 | 便于连续分配，适合存活对象较少的场景 | 需要预留复制空间，存活对象多时复制成本较高 |
| 标记—整理 | 标记存活对象，将其向一端移动，回收剩余空间 | 减少内存碎片 | 移动对象并更新引用有额外开销 |

简单的半区复制会将内存分成两半，每次只使用一半，但实际回收器可以采用不同布局，不一定浪费一半空间。

**分代回收**：利用“大多数对象很快死亡，少量对象长期存活”的特点，将堆按代管理。新生代通常采用复制思路，老年代根据回收器使用清除、整理等方式。

在常见分代回收器中，对象在 Survivor 中经历回收后仍存活，年龄会增加；达到晋升条件时进入老年代。`-XX:MaxTenuringThreshold` 用于限制晋升年龄阈值，实际阈值可能动态调整，也可能因 Survivor 空间不足等原因提前晋升，不能把“存活 15 次才进入老年代”视为固定规则。

## 四、垃圾回收器有哪些？

常见的 HotSpot 回收器如下，实际支持情况取决于 JDK 版本和发行版。

| 回收器 | 管理范围与主要算法 | 特点 |
| --- | --- | --- |
| Serial / Serial Old | 新生代复制、老年代标记—整理 | 单线程回收，暂停应用线程，适合小堆、资源有限的场景 |
| ParNew | 新生代复制 | 多线程并行回收，历史上主要与 CMS 配合 |
| Parallel Scavenge / Parallel Old | 新生代复制、老年代标记—整理 | 多线程并行回收，吞吐量优先，适合批处理等任务 |
| CMS | 老年代标记—清除 | 大部分阶段与应用并发，减少停顿，但有碎片和并发失败等问题；JDK 14 已移除 |
| G1 | 整堆按 Region 管理，通过复制疏散存活对象 | 兼顾吞吐量与停顿目标，适合常见服务端应用 |
| ZGC | 整堆并发标记、重定位 | 低停顿，适合对延迟敏感的应用，但仍需要 CPU 和内存余量 |
| Shenandoah | 整堆并发标记、整理 | 低停顿，具体可用性取决于 JDK 构建及平台 |

**并行**是多个 GC 线程一起工作，此时应用线程可能暂停；**并发**是 GC 的部分工作与应用线程同时进行，仍可能有短暂的 Stop-The-World 阶段。

版本方面，G1 从 JDK 9 起成为服务端默认回收器；CMS、ParNew 主要作为历史知识了解。ZGC 在 JDK 11 实验性引入、JDK 15 转为正式特性，JDK 21 引入分代模式，JDK 23 默认使用分代 ZGC，JDK 24 移除非分代模式。

选择时，吞吐量优先可以评估 Parallel，常见服务可以从 G1 开始，低延迟需求可以评估 ZGC 或 Shenandoah。最终应结合实际负载压测，低停顿目标并不等于任意负载下都保证固定的暂停时间。

参考：[OpenJDK ZGC 文档](https://wiki.openjdk.org/pages/viewpage.action?pageId=34668579)、[JEP 363：移除 CMS](https://openjdk.org/jeps/363)。

## 五、Minor GC、Major GC、Full GC 有什么区别？什么场景触发 Full GC？

这些术语并非所有回收器都统一使用，需要结合具体回收器和 GC 日志理解。

| 类型 | 通常含义 | 说明 |
| --- | --- | --- |
| Minor GC / Young GC | 回收新生代 | 常由新生代分配空间不足触发，存活对象可能转移到 Survivor 或晋升老年代 |
| Major GC / Old GC | 通常指老年代回收 | 部分资料也用它指 Full GC，因此不能仅凭名称判断范围 |
| Full GC | 对整个 Java 堆进行回收 | 通常停顿较长，可能伴随类卸载，但不保证回收所有元空间数据 |

G1 的 **Mixed GC** 同时回收年轻代和选中的部分老年代 Region，不等于 Full GC。ZGC 等回收器也不能简单套用传统的三类划分。

常见的 Full GC 触发场景包括：

- **堆分配或对象晋升无法完成**：常规回收仍无法腾出足够空间时，可能进行全堆回收；G1 疏散失败等情况也可能导致 Full GC。
- **元空间分配压力**：JVM 可能尝试通过支持类卸载的 GC 释放元数据空间，具体是否 Full GC 取决于实现和配置。
- **显式 GC 请求**：`System.gc()` 在部分配置下会触发 Full GC，也可能启动并发回收或被忽略，不能保证其回收类型。
- **历史上的 CMS 失败**：并发回收赶不上分配速度等情况，可能回退到停顿式老年代回收；CMS 已在 JDK 14 移除。

频繁 Full GC 应结合日志排查：是否存在内存泄漏、缓存或队列无界增长、晋升压力过大、堆配置不合理，或不必要的显式 GC 请求，再针对原因优化。

## 六、GC 只会回收堆吗？

不是。GC 主要回收堆中的对象，也可能涉及方法区相关数据的回收。

- **堆**：回收满足条件的对象实例和数组，是垃圾回收的主要区域。
- **方法区相关数据**：在支持并启用类卸载时，JVM 可以卸载不再使用的类。JDK 8 起，HotSpot 的类元数据主要位于元空间，类卸载后可释放相关元数据空间。

类卸载需要满足相应的可达性条件，例如定义该类的类加载器可以被回收；并不是某个类暂时没有调用，就会被卸载。静态字段的值和驻留字符串在现代 HotSpot 中位于堆中，不能笼统地说它们都由元空间回收。

程序计数器和线程栈随线程及方法执行管理，不依靠堆 GC 回收。直接内存也不属于堆，部分资源可以借助 Cleaner 等机制清理，但不能把堆 GC 当作所有本地资源的通用释放方式。
